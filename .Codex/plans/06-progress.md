Изображения, цены, расписания и возрастные ограничения остаются отдельными
структурированными данными.

Подтверждена модель цены `ServiceOffer`: `priceType` принимает `FIXED`, `FROM`,
`FREE`, `INCLUDED` или `ON_REQUEST`; сумма хранится в копейках в nullable `amount`,
единица расчёта и примечание остаются отдельными строками. Валюта первой версии — RUB.

Подтверждена модель `ServiceSchedule`: `RECURRING` хранит массив дней недели,
локальные строки времени `HH:mm` и необязательный сезонный период; `ON_REQUEST`
хранит публичную формулировку «по согласованию». Разовые события остаются
новостями/анонсами.

Подтверждена модель возраста: границы хранятся в полных месяцах; `ServiceOffer`
может наследовать возраст услуги, задать собственный диапазон или явно не иметь
ограничения.

Подтверждена стратегия жизненного цикла: `Service` использует `isPublished` и
`archivedAt`; обычное удаление архивирует запись, постоянное удаление не входит
в API первой версии. Вложенные группы, предложения и расписания публикуются
отдельно и могут удаляться физически с `Cascade`; заявки сохраняются.

Подтверждён и внесён полный состав полей `Service`, `ServiceOfferGroup`,
`ServiceOffer` и `ServiceSchedule`, а также изменения `Teacher`, `GalleryItem` и
`Lead`. Для `DayOfWeek` выбраны английские значения от `MONDAY` до `SUNDAY` в
ISO-порядке. При физическом удалении `Service` связанная запись `GalleryItem`
удаляется через `Cascade`; сам файл в хранилище этим не удаляется.

| Решение | Обоснование |
|---|---|
| **После завершения основного плана обязательно напомнить о MVP геймификации** | Решение пользователя от 30.08.2026. Возможность не входит в текущие шаги 1–29 и рассматривается только после подтверждения завершения основной части. Зафиксированный MVP: игровой подбор услуги «Подбери приключение», бумажный «Паспорт Минимишек» и ежемесячное семейное задание. Проектирование и реализация начинаются только после отдельного согласования |
| **Prisma 6.19.3**, а не 7.x | Решение пользователя из двух предложенных вариантов. В npm `latest` — 7.9.1, и она устроена иначе: генератор `prisma-client` вместо `prisma-client-js`, обязательный `output` (клиент генерируется в исходники проекта, а не в `node_modules`), строка подключения убрана из схемы в отдельный `prisma.config.ts` плюс зависимость `dotenv`. Проверено запуском `prisma@7.9.1 init` в песочнице. Взяли 6-ю ветку: схема из [`04-domain-model.md`](./04-domain-model.md) идёт без правок, клиент импортируется привычно из `@prisma/client`, материалы в сети — про неё же. Переход на 7 — в [`08-backlog.md`](./08-backlog.md) |
| **`"dependsOn": ["^build"]` у задачи `dev`** в `turbo.json` | Решение пользователя, закрывает открытый вопрос сессии 5. Крышка — «в зависимостях пакета», то есть перед `dev` собирается `@minimishki/shared`, иначе на чистом репозитории API падает на `Cannot find module '@minimishki/shared'`. Ограничение turbo не нарушено: зависеть **от** persistent-задач нельзя, а `build` — обычная. Побочный плюс: у `shared` есть свой `dev` (`tsc --watch`), поэтому правки общих типов теперь подхватываются без ручной пересборки |
| **Имя пакета бэкенда — `api`**, без области `@minimishki/` | В корневом `package.json` уже записаны `pnpm --filter api db:migrate` и ещё три команды `db:*`. Фильтр сопоставляется с полем `name` — с `@minimishki/api` все они перестали бы находить пакет |
| **`rootDir: "./src"` в `apps/api/tsconfig.json`** + отдельный `tsconfig` для сида | Из двух вариантов, записанных на шаге 7, выбран второй. `rootDir` фиксирует форму вывода: `src/main.ts` → `dist/main.js`, и `entryFile: "main"` в `nest-cli.json` попадает в цель. Без него корень вычисляется как общий предок включённых файлов — добавление `prisma/seed.ts` молча переехало бы в `dist/src/main.js`. Сид использует собственный `prisma/tsconfig.json`; он нужен ещё и линтеру: `projectService` ищет ближайший вверх по дереву `tsconfig.json`, а корневой конфиг приложения сид исключает |
| **Конфиг Prisma — `prisma.config.mjs`**, а не `.ts` | Решение пользователя на шаге 19. Prisma 6.19.3 поддерживает `.mjs`; функционально он равнозначен `.ts`, но уже попадает под существующее исключение type-aware ESLint для JavaScript-конфигов. Вариант `.ts` лежал бы вне `include` основного `apps/api/tsconfig.json` и потребовал бы отдельной настройки ESLint либо ещё одного TypeScript-проекта |
| **Prisma CLI загружает `.env` через прямую dev-зависимость `dotenv`** | При наличии `prisma.config.*` Prisma не загружает `.env` автоматически. `import 'dotenv/config'` выполняется до `defineConfig`, поэтому `migrate`, `studio`, `generate` и `db seed` получают `DATABASE_URL` и seed-переменные. Прямая зависимость обязательна при строгой изоляции pnpm; полагаться на транзитивный `dotenv` из `@nestjs/config` нельзя |
| **Demo-seed работает только в development/test** | Решение пользователя и исправление код-ревью шага 19. Seed — отдельный процесс без Nest `ConfigModule`, поэтому валидирует `NODE_ENV` и `SEED_ADMIN_*` сам. В development/test разрешены согласованные значения по умолчанию; при `NODE_ENV=production` выполнение запрещено до первого SQL-запроса. Production-bootstrap администратора будет отдельным сценарием без вымышленных данных |
| **Seed содержит временные вымышленные данные** | Решение пользователя: реальные направления, педагоги, новости и фотографии появятся позже. Пока используются нейтральные демонстрационные записи и относительные пути `/images/demo/*`; все сущности создаются через `upsert`, связи педагогов синхронизируются через `set`, галерея пересоздаётся без накопления дубликатов |

Записано декларативно в `package.json`, а не через интерактивный `pnpm approve-builds`: настройка едет вместе с репозиторием. `unrs-resolver` остаётся в `ignoredBuiltDependencies` — ему скрипт не нужен |
